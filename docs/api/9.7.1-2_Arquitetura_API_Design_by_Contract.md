## 1. Visão Geral da Arquitetura

O módulo **Hort-IA** adota o modelo arquitetural de **Microsserviço Especialista de Inteligência Artificial**. Ele é construído sobre **Python 3.14** utilizando o framework **FastAPI** e o motor de validação **Pydantic v2**.

A comunicação com os módulos consumidores (Assistência Técnica, Comercialização, Gestão e Planejamento Financeiro) dá-se por meio de **APIs RESTful orientadas a contratos previsíveis**.

```
                           CONSUMIDORES
        (Mobile / Web / Backend Java Spring Boot)
                            │
                            │  HTTPS / JSON & Multipart
                            ▼
     ┌─────────────────────────────────────────────────────────────┐
     │              FastAPI Gateway & OpenAPI Router               │
     │                                                             │
```

## 2. Princípios de Design by Contract (DbC) Aplicados

A metodologia **Design by Contract (DbC)** (Bertrand Meyer) estabelece que todo componente de software deve operar mediante um compromisso formal entre chamador e provedor, estruturado em três pilares fundamentais:

### 2.1. Pré-condições (O que o consumidor é obrigado a fornecer)
O consumidor deve atender rigorosamente aos tipos, limites numéricos e formatos exigidos antes que a IA processe a requisição:
* **Tipos de Arquivo Válidos:** Apenas streams binários do tipo `image/jpeg`, `image/png` ou `image/webp` não vazios (erro HTTP 415 em caso de violação).
* **Limites Numéricos e Domínios:**
  * Meses do ano: inteiros de `1` a `12`.
  * Códigos de Município IBGE: strings numéricas de 7 dígitos válidas, cujo primeiro dígito mapeie uma macrorregião (1 a 5).
  * Horizontes de previsão financeira: estritamente `1` ou `3` meses (erro HTTP 422 em caso de horizonte não validado).
* **Identificadores Canônicos:** Identificadores de produtos e entrepostos devem existir no catálogo canônico da base de dados (erro HTTP 404 em caso de id inexistente).

### 2.2. Pós-condições (O que o Hort-IA garante entregar)
Se as pré-condições forem cumpridas, o Hort-IA garante inviolavelmente:
* **Dimensões e Tamanho Padronizados:** Em rotas de pré-processamento de imagens, a saída terá rigorosamente $224 \times 224$ pixels, 3 canais de cor RGB, compressão JPEG de qualidade 85 e peso inferior a 30 KB.
* **Rastreabilidade e Não-Alucinação:** Toda resposta contém metadados de auditoria:
  * `source`: ID ou citação bibliográfica da fonte (ex.: Embrapa, Boletim Conab Prohort);
  * `model_version`: versão semântica do modelo utilizado (ex.: `1.0.0`);
  * `handoff`: flag booleana explícita indicando se a IA possui dados para a resposta (`False`) ou se a solicitação deve ser encaminhada para assistência técnica humana (`True`).
* **Valores Econômicos Consistentes:** Preços sempre expressos em Reais por quilograma (R$/kg) positivos e arredondados em duas casas decimais.

### 2.3. Invariantes (O que sempre deve ser verdadeiro em qualquer estado)
* **Invariante de Privacidade (LGPD):** Nenhum dado de geolocalização por satélite (EXIF GPS) ou identificador biométrico de câmera trafega ou reside após a borda do microsserviço.
* **Invariante de Isolamento:** A base de dados de mercado (`data/market`) é desacoplada da base de conhecimento (`data/knowledge`), comunicando-se exclusivamente pelo identificador canônico `crop_id`.
* **Invariante Temporal:** Modelos preditivos de séries temporais nunca realizam extrapolação (*look-ahead bias*) nas bordas das séries.

## 3. Padrão Uniforme de Tratamento de Erros

Para evitar respostas ambíguas aos módulos consumidores, todos os erros retornados pela API utilizam um modelo semântico previsível e tipado inspirado na **RFC 7807** (*Problem Details for HTTP APIs*):

```json
{
  "status_code": 422,
  "error_type": "UnprocessableEntityError",
  "detail": "Imagem rejeitada pelo controle de qualidade: Foto borrada ou fora de foco.",
  "user_feedback": "A imagem está fora de foco. Toque na tela para focar a câmera antes de tirar a foto.",
  "timestamp": "2026-10-23T17:30:00Z"
}
```

### Códigos de Status HTTP Padronizados:

| Status Code | Semântica | Quando é Retornado |
| :---: | :--- | :--- |
| **200 OK** | Sucesso | Requisição processada com sucesso; payload de resposta entregue conforme o contrato. |
| **400 Bad Request** | Erro de Sintaxe | Arquivo enviado vazio, JSON corrompido ou payload mal formatado. |
| **404 Not Found** | Não Encontrado | Produto, cultura, entreposto ou município solicitado não existe na base de dados. |
| **415 Unsupported Media Type** | Mídia Não Suportada | Upload de formato de imagem não aceito (ex.: GIF, BMP, PDF). |
| **422 Unprocessable Entity** | Violação de Regra de Negócio | Qualidade da foto abaixo do limiar (borrada/escura), horizonte fora de 1 ou 3 meses. |
| **500 Internal Server Error** | Falha Inesperada | Erro não capturado na execução interna dos modelos (registrado em logs para depuração). |

## 4. Estratégia para Conectividade Limitada e Dispositivos Móveis

Para cumprir a exigência do TAP de viabilizar a operação em hortas periféricas com sinal de celular fraco (3G/4G instável):

1. **Protocolo Leve e Stateless:** Todos os endpoints são estritamente desacoplados de sessões no servidor (*stateless*), permitindo que requisições sejam facilmente repetidas ou roteadas por caches intermediários.
2. **Controle de Cache HTTP (`Cache-Control` e `ETag`):**
   * Endpoints de dados agronômicos estáticos (calendário de plantio e consórcios) fornecem cabeçalhos `Cache-Control: public, max-age=86400` (cache de 24h no celular/app).
   * As cotações da Conab fornecem `Cache-Control: public, max-age=3600` (cache de 1h), economizando pacotes de dados 3G do agricultor.
3. **Injeção de Metadados de Modo Degradado (`degraded` e `warning`):**
   * Quando uma série histórica é curta (< 22 meses), o contrato financeiro devolve `degraded: true` e omite os intervalos estatísticos, permitindo que a aplicação consumidora informe ao produtor que aquela previsão é simplificada (Naive).
