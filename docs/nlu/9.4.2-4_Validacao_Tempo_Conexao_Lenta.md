# Validação do tempo de resposta em conexão lenta (WBS 9.4.2-4)

> **Entregável:** 9.4.2-4 Validar tempo de resposta em cenário de conexão lenta
> **Pacote de trabalho:** 9.4.2 · **Marco:** M9.4 (30/11/2026) · **Responsável:** Renato Gouveia
> **Versão 1.0 — 06/11/2026** (planejada para 23/11/2026; 3 h)
> **Status:** concluído. **Os perfis de rede são premissas da equipe (seção 2) e dependem de aprovação**

Reproduzir: `uv run python scripts/measure_slow_connection.py` (alguns minutos). Números completos:
[9.4.2-4_slow_connection_metrics.json](9.4.2-4_slow_connection_metrics.json). Os testes de
`tests/test_nlu_slow_connection.py` mantêm a conclusão válida quando o código mudar.

## 1. Conclusão

O critério da entrega 9.4 pede **tempo médio de resposta abaixo de 5 s**, inclusive em conexão
lenta (Dicionário da EAP). Resultado:

- **Atendido em todos os perfis realistas**, mesmo no pior arranjo de cliente: uma conexão HTTPS nova
  a cada mensagem. Em 2G, a média fica em **3,3 s**; em 3G lento, em **1,6 s**.
- **O motor não é o gargalo:** responde em **2,7 ms** por mensagem. O tempo é quase todo da rede, e
  cada mensagem custa pelo menos uma ida e volta (RTT).
- **Só o perfil de estresse** (2 s de RTT, 50 kbit/s) passa da meta, e **só** quando o cliente abre
  uma conexão nova a cada mensagem: 8,2 s com HTTPS. Reaproveitando a conexão, a média cai para 2,5 s.
  Daí a recomendação principal da seção 5.

## 2. Método

Um proxy TCP (`scripts/measure_slow_connection.py`) fica entre o cliente e a API (uvicorn) e simula a
rede nos dois sentidos: atrasa cada pacote em meio RTT, cobra um RTT para abrir cada conexão (como o
aperto de mão do TCP) e limita a banda, byte a byte. O cliente mede o tempo entre enviar a mensagem e
receber a resposta inteira.

**Perfis** (premissas da equipe, do 4G fraco a um caso de estresse):

| Perfil | RTT | Download | Upload |
|---|---|---|---|
| 4G fraco | 150 ms | 1,6 Mbit/s | 750 kbit/s |
| 3G lento | 400 ms | 400 kbit/s | 400 kbit/s |
| 2G (EDGE) | 800 ms | 100 kbit/s | 50 kbit/s |
| Pior caso (estresse) | 2.000 ms | 50 kbit/s | 25 kbit/s |

**Mensagens:** as 21 mensagens das conversas de referência de 9.4.1-3 (M1 a M6 e C1 a C8), com o
`context` indo e voltando como faria a interface, e uma chamada a `POST /recommender/recommendations`.

**Dois arranjos de cliente:** conexão nova para cada mensagem (pior caso) e conexão reaproveitada
(*keep-alive*).

**HTTPS** não é simulado pelo proxy. O custo foi somado à medição: abrir uma conexão segura exige 1
RTT a mais com TLS 1.3 e 2 com TLS 1.2. As tabelas usam o TLS 1.2, o pior dos dois.

**Limites do método:** não há perda de pacotes nem variação de atraso (*jitter*); não entram o tempo
do celular nem o da interface. Na arquitetura prevista, quem chama a API de IA é o servidor do módulo
consumidor, e o trecho lento é entre o celular e esse servidor. Medir como se o celular falasse direto
com a API é, portanto, um limite superior para a parte que cabe ao módulo de IA.

## 4. Onde vai o tempo

Em 2G com conexão nova, uma mensagem gasta 1,6 s em duas idas e voltas (abrir a conexão; enviar e
receber) e cerca de 0,1 s transferindo bytes. Um modelo com essas duas parcelas reproduz a medição
do proxy com diferença de 0,01 s, e é ele que os testes usam.

- **Tamanho:** a maior resposta do assistente tem 1,7 KB ("o que dá pra plantar agora?", em que 1,1
  KB são as fontes citadas); as demais ficam entre 0,4 e 0,7 KB. A requisição, com o `context`, chega
  a 350 bytes. A lista de recomendações tem 4 KB.
- **Turnos de confirmação** ("Você quis dizer alface?") custam uma mensagem a mais, ou seja, pelo
  menos mais um RTT. No pior caso, são 2 s a mais a cada confirmação. É mais um motivo para calibrar
  os limiares com dados reais (9.4.2-2, U6) e acompanhar a proporção de confirmações no UAT.

## 5. Recomendações

Para o módulo consumidor e para a integração (9.7), em ordem de efeito:

1. **Reaproveitar a conexão** com a API (*keep-alive* ou HTTP/2). É o que tira o pior caso de 8,2 s
   para 2,5 s e corta quase pela metade o tempo nos outros perfis.
2. **Usar TLS 1.3**, que economiza um RTT a cada conexão nova.
3. **Aquecer a API ao subir:** a primeira mensagem treina o classificador. Uma chamada a
   `get_dialogue()` na inicialização da aplicação (`lifespan` do FastAPI, em `api/main.py`) tira esse
   custo do primeiro usuário.

Para o módulo de IA, os testes de `tests/test_nlu_slow_connection.py` impedem que as mensagens
cresçam sem que se perceba: resposta do assistente até 4 KB, requisição até 1 KB, recomendações até
8 KB, e tempo modelado em 2G com HTTPS e conexão nova abaixo de 5 s em cada mensagem de referência.

## 6. Reproduzir

```bash
uv run python scripts/measure_slow_connection.py    # mede com o proxy e grava o JSON
uv run pytest tests/test_nlu_slow_connection.py -v  # orçamentos de tamanho e tempo modelado
```
